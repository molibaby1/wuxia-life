# P2 玩法结构与持久化体验 PRD

## 1. 背景

P0 聚焦核心体验止血，P1 聚焦事件质量、节奏、格式和条件执行。用户已说明 P1 在其他会话中完成实施。P2 阶段进入玩法结构增强，但仍不做大规模内容扩写或 UI 重构。

P2 关注四类能力：

- 玩家选择后的反馈闭环：让玩家理解即时结果、长期影响、路线变化和关系变化。
- 人生路线与身份系统：让商人、侠客、门派、魔道、官场等路线具备互斥、延续和完成判定。
- 真实游玩模拟测试：用固定种子和指标衡量 0-80 岁人生是否稳定、可玩、可解释。
- 存档系统接入真实主流程：确保新游戏、保存、读取、继续、重开、结局状态一致。

本 PRD 仅定义 P2 阶段方案和 Ralph user stories。未获得审批前，不进入业务代码实施。

## 2. P2 目标

1. 建立结构化选择反馈模型，明确即时反馈和长期影响。
2. 建立人生路线与身份的互斥、推进、完成和断线规则。
3. 建立真实游玩模拟指标，覆盖路线完成率、选择率、死亡率、结局分布等。
4. 将存档系统接入真实主流程，并验证保存/读取后的状态一致性。
5. 形成 P2 质量报告，为 P3 UI 与工程整理提供依据。

## 3. 非目标

- 不新增大规模剧情内容。
- 不重做主界面整体信息架构。
- 不拆分整个核心引擎类。
- 不清理历史文档体系。
- 不引入外部数据库或云存档。
- 不做商业化、账号、联网同步。

## 4. 前置条件

P2 实施前应确认：

- P0 与 P1 的关键 user stories 已完成或被项目负责人明确豁免。
- 默认验证命令可运行。
- P1 的事件质量门禁和节奏报告可作为 P2 设计基础。
- 当前主流程状态源已明确，存档接入不会依赖旧状态链路。

若 P1 在当前工作树中缺少可验证证据，P2 的第一项任务必须先补基线确认，不应直接改动玩法结构。

## 5. 范围

### 5.1 In Scope

- 选择反馈字段、展示规则、测试样本和回归测试。
- 路线、身份、阵营、关键选择之间的关系盘点。
- 主路线、副路线、冲突路线、路线锁定、路线完成和路线断线规则。
- 真实游玩模拟指标、报告、固定种子、阈值和门禁策略。
- 存档主流程接入、状态版本、保存/读取/继续/重开验证。
- P2 交付报告与残余风险列表。

### 5.2 Out of Scope

- 大规模新增剧情线。
- 大范围改 UI 布局。
- 完整重写事件引擎。
- 跨设备云同步。
- 全量历史存档迁移。
- P3 的文档归档、UI 信息架构重整和引擎拆分。

## 6. 用户故事

### US-001：确认 P1 基线与 P2 入口条件

作为维护者，我希望在进入 P2 前确认 P1 已完成并且验证命令可运行，这样 P2 不会建立在未收口的质量治理上。

验收标准：
- 读取 P1 PRD 和 P1 实施证据或交付说明。
- 记录 P1 入口状态：完成、部分完成、豁免或阻塞。
- 若 P1 证据不足，明确列出 P2 受影响故事。
- 不修改业务代码。

优先级：1

### US-002：盘点当前选择反馈来源

作为开发者，我希望知道选择结果文本、效果、关系变化、路线变化来自哪里，这样反馈闭环设计不会重复造字段。

验收标准：
- 盘点选择事件、outcome、effect、lastOutcomeText、事件历史、关系和路线变更来源。
- 标记每类反馈是即时反馈、长期反馈、隐藏反馈还是调试信息。
- 输出当前缺口清单。
- 不修改业务代码。

优先级：2

### US-003：定义结构化选择反馈模型

作为玩家，我希望选择后能理解发生了什么、损失了什么、开启了什么，这样选择才有分量。

验收标准：
- 定义反馈模型字段：叙事结果、数值影响、关系影响、路线影响、长期旗标、风险提示。
- 明确哪些字段面向玩家展示，哪些字段仅用于日志或测试。
- 明确反馈缺失时的兜底规则。
- 写入设计说明。

优先级：3

### US-004：实现选择反馈生成器

作为开发者，我希望有统一反馈生成入口，这样选择、自动判定、模拟报告不会各写各的反馈逻辑。

验收标准：
- 新增或收敛统一反馈生成入口。
- 选择事件和自动选择事件能生成同一结构的反馈。
- 不直接向玩家暴露原始调试字段。
- 类型检查通过。

优先级：4

### US-005：接入主界面选择反馈展示

作为玩家，我希望在选择后看到清晰结果和关键长期影响，而不是泛泛一句话。

验收标准：
- 主流程选择结果展示结构化反馈。
- 数值、关系、路线等影响展示遵守设计规则。
- 无反馈数据时显示合理叙事兜底。
- 构建通过。

优先级：5

### US-006：补充选择反馈回归测试

作为维护者，我希望选择反馈有测试覆盖，这样后续事件内容不会重新变成模糊反馈。

验收标准：
- 测试覆盖数值变化、关系变化、路线变化、长期旗标、兜底文本。
- 测试覆盖选择事件和自动判定事件。
- 默认测试门禁通过。

优先级：6

### US-007：盘点路线、身份、阵营和关键选择字段

作为设计者，我希望先看清当前路线和身份字段，这样互斥规则不会误伤已有内容。

验收标准：
- 盘点身份、路线、阵营、门派、关键选择、karma、关系字段。
- 标记字段来源、写入点、读取点和数据含义。
- 标记主流程使用、历史兼容、疑似废弃三类。
- 不修改业务代码。

优先级：7

### US-008：定义路线分类与生命周期

作为玩家，我希望人生路线有开始、发展、锁定、转向、完成或失败，这样每局人生有清晰形状。

验收标准：
- 定义主路线、副路线、冲突路线、临时状态、完成状态、失败状态。
- 明确路线生命周期状态机。
- 明确路线何时可切换、何时锁定、何时结束。
- 写入设计说明。

优先级：8

### US-009：定义路线互斥与兼容规则

作为设计者，我希望路线之间的冲突和兼容关系明确，这样玩家不会同时成为互相矛盾的身份。

验收标准：
- 定义至少商人、侠客、门派、魔道、官场、隐士或游侠的冲突/兼容关系。
- 明确强互斥、软互斥、可共存关系。
- 明确冲突发生时的处理规则。
- 写入可测试规则表。

优先级：9

### US-010：实现路线状态管理基础

作为开发者，我希望路线状态有统一管理入口，这样事件效果不会到处手写路线 flag。

验收标准：
- 提供路线状态读取、写入、锁定、完成、失败的统一入口。
- 不破坏既有身份和阵营字段。
- 关键状态变化可记录到事件历史或路线历史。
- 类型检查通过。

优先级：10

### US-011：接入路线互斥判定

作为玩家，我希望已经锁定的路线能影响后续事件和选择，这样人生选择有持续后果。

验收标准：
- 冲突路线事件不会在不合理状态下触发。
- 软互斥路线可以通过明确转向事件处理。
- 关键路线锁定后有可追踪状态。
- 默认测试门禁通过。

优先级：11

### US-012：补充路线推进与断线测试

作为设计者，我希望路线完成率和断线率可被测试，这样路线系统不是只靠手感。

验收标准：
- 测试覆盖路线开始、推进、锁定、冲突阻断、完成、失败或断线。
- 至少覆盖两类不同路线。
- 默认测试门禁通过。

优先级：12

### US-013：定义真实游玩模拟指标

作为维护者，我希望真实游玩模拟指标覆盖玩法结构，而不仅是流程能跑。

验收标准：
- 指标包含选择率、自动事件率、路线完成率、路线断线率、死亡率、结局分布、婚恋/家庭达成率、存档次数。
- 指标包含目标区间或观察基线。
- 指标能区分 blocker、warning、info。

优先级：13

### US-014：实现固定种子真实游玩模拟

作为开发者，我希望真实游玩模拟可重复，这样回归结果可以对比。

验收标准：
- 支持固定随机种子。
- 支持指定年龄范围或完整人生模拟。
- 输出机器可读结果和人类可读摘要。
- 不依赖浏览器 UI 即可运行。

优先级：14

### US-015：增加多路线模拟样本

作为设计者，我希望模拟覆盖不同出身、路线和选择倾向，这样只测一条人生不会误判稳定性。

验收标准：
- 至少定义三类模拟画像或选择策略。
- 每类样本输出路线、结局、选择、死亡和关系摘要。
- 样本可通过命令重复运行。

优先级：15

### US-016：建立模拟结果阈值与门禁

作为维护者，我希望真实游玩模拟能判断失败，而不只是生成漂亮报告。

验收标准：
- 定义哪些指标失败会阻断验证。
- 定义哪些指标只输出 warning。
- 支持豁免清单并要求说明原因。
- 默认测试门禁通过。

优先级：16

### US-017：盘点当前存档状态结构

作为开发者，我希望先确认存档保存了哪些状态，这样接入主流程不会漏掉路线、关系或事件历史。

验收标准：
- 盘点保存字段、读取字段、版本字段、缺失字段和派生字段。
- 覆盖玩家、当前事件、事件历史、路线、身份、关系、结局、时间。
- 不修改业务代码。

优先级：17

### US-018：定义存档版本与兼容边界

作为维护者，我希望明确 P2 存档版本策略，这样未来变更不会让旧存档无声损坏。

验收标准：
- 定义 P2 存档版本号或 schema 标识。
- 定义允许读取的旧版本范围。
- 定义不支持旧版本时的用户提示和失败方式。
- 明确本阶段不做全量历史迁移。

优先级：18

### US-019：接入主流程保存与读取

作为玩家，我希望能在真实游戏流程中保存并读取进度，这样长线人生模拟可持续游玩。

验收标准：
- 主流程可保存当前人生状态。
- 可从存档恢复玩家、时间、事件历史、路线、关系和结局相关状态。
- 读取后继续游戏不会重置关键状态。
- 类型检查通过。

优先级：19

### US-020：接入重开、继续与结局后的存档行为

作为玩家，我希望重开、继续和结局后的存档行为一致且可预测。

验收标准：
- 重开不会污染已有存档。
- 读取存档后继续流程状态正确。
- 结局后存档显示或读取行为符合设计。
- 构建通过。

优先级：20

### US-021：补充存档回归测试

作为维护者，我希望存档系统有回归测试，这样路线、关系和事件历史不会在读取后丢失。

验收标准：
- 测试覆盖保存、读取、继续、重开、结局后读取。
- 测试覆盖路线、身份、关系、事件历史、时间字段。
- 默认测试门禁通过。

优先级：21

### US-022：将存档纳入真实游玩模拟

作为开发者，我希望模拟过程中能周期性保存和恢复，这样可以验证真实长线体验。

验收标准：
- 模拟支持按年龄或事件间隔自动保存。
- 至少一次从存档恢复后继续模拟。
- 报告包含保存次数、读取次数和一致性检查结果。
- 默认测试门禁通过。

优先级：22

### US-023：生成 P2 玩法结构报告

作为项目负责人，我希望 P2 结束时看到玩法结构证据，这样可以判断是否进入 P3。

验收标准：
- 报告包含选择反馈覆盖、路线完成率、路线断线率、模拟指标、存档一致性。
- 报告列出残余风险。
- 报告明确 P3 候选事项。

优先级：23

### US-024：P2 收口验证

作为维护者，我希望 P2 完成后有完整验证证据，这样后续会话可以安全接力。

验收标准：
- `npm run typecheck` 通过。
- `npm run build` 通过。
- `npm test` 通过。
- P2 新增模拟/存档/路线质量命令通过或输出已审批豁免。
- P2 PRD JSON 中完成的 user stories 更新验证状态或交付说明记录完成证据。

优先级：24

## 7. 推荐实施顺序

1. US-001：确认 P1 基线。
2. US-002 至 US-006：先建立选择反馈闭环。
3. US-007 至 US-012：再建立路线与身份结构规则。
4. US-013 至 US-016：补真实游玩模拟指标与门禁。
5. US-017 至 US-022：接入存档主流程并纳入模拟。
6. US-023 至 US-024：报告与收口验证。

说明：存档接入依赖路线状态和反馈状态边界清晰，因此放在 P2 后半段实施。

## 8. 验证计划

P2 默认验证命令：

```bash
npm run typecheck
npm run build
npm test
```

P2 实施中新增的模拟、路线和存档验证命令应满足：

- 可在本地直接运行。
- 支持固定种子或固定输入。
- 输出人类可读摘要。
- 对 blocker 问题返回失败状态。
- 可被后续发布门禁复用。

## 9. 风险与缓解

### 风险 1：选择反馈暴露过多数值，破坏叙事感

缓解：区分玩家展示字段和测试/日志字段。玩家界面展示叙事化摘要，测试保留结构化明细。

### 风险 2：路线互斥规则误伤已有剧情

缓解：先盘点字段和事件，再定义规则。先覆盖少数核心路线，逐步扩展，不做一次性全量封锁。

### 风险 3：真实模拟指标过严导致持续失败

缓解：先建立观察基线，再逐步提升阈值。将 blocker、warning、info 分级。

### 风险 4：存档接入暴露历史状态不一致

缓解：明确 P2 存档版本边界，不做无限兼容。读取失败要显式提示，不静默降级。

### 风险 5：P2 范围膨胀到 UI 重构或引擎拆分

缓解：P2 只定义结构和可靠性。UI 信息架构、文档归档和引擎拆分留给 P3。

## 10. 回滚策略

- 选择反馈：按反馈生成器或展示接入点回滚，保留测试样本。
- 路线规则：按规则配置或路线管理入口回滚，不大面积删除事件内容。
- 模拟门禁：可先回滚阻断阈值，保留报告输出。
- 存档接入：按保存/读取入口回滚，保留版本说明和失败提示。

## 11. 审批边界

本文档和配套 Ralph JSON 仅定义 P2 阶段方案。未获得明确审批前，不进入业务代码修改。

跨会话继续 P2 时，必须先读取本文档和配套 JSON，并按 user stories 优先级顺序实施。
