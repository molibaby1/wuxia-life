# 体验治理分布式执行 PRD

## 1. 背景

项目已经完成 P0、P1、P2 的多项结构治理：事件质量、节奏基线、选择反馈、路线状态、存档接入和真实游玩模拟均有代码或文档证据。但当前只读分析显示，核心体验仍存在明显错位：

- 事件系统结构更完整，但同一事件、同类事件和同阶段高权重事件仍会复读。
- 节奏报告和模拟报告能运行，但 formal 事件长期接管主流程，daily 事件空间不足。
- 路线状态和互斥规则存在，但真实事件池没有形成足够的路线接管力。
- 自动化验证能证明结构存在和命令通过，却不能稳定阻断坏体验。

本 PRD 定义一个跨多会话的体验治理阶段。该阶段不追求一次性重写，而是把体验问题拆成可分发、可验收、可回归的执行包。

## 2. 目标

1. 统一事件生命周期门禁，降低同一事件、同类事件和生命周期事件复读。
2. 调整年龄段和候选池节奏，让正式事件、日常事件、剧情线事件形成更健康分布。
3. 让路线系统从状态字段升级为主流程体验调度因素。
4. 升级体验验证，让“测试通过但体验不健康”的问题可被发现、定位和阻断。
5. 为后续内容扩展建立稳定的体验健康基线。

## 3. 非目标

- 不做大规模剧情文案扩写。
- 不重做 UI 信息架构。
- 不拆分整个核心引擎类。
- 不引入新框架或外部服务。
- 不一次性迁移全部历史事件格式。
- 不删除历史文档或报告。

## 4. 范围

### 4.1 In Scope

- 事件生命周期、冷却、最大触发次数、flag 门禁、事件历史记录口径。
- 年龄段事件池、候选池排序/截断、formal/daily/storyline 分布。
- 路线事件加载、路线目标元数据、路线生命周期完成/失败/锁定路径。
- 真实游玩模拟指标、体验诊断、固定 seed、多 persona、多阶段回归样本。
- 体验健康门禁阈值和 waiver 规则。

### 4.2 Out of Scope

- 全量新增门派、身份和结局。
- UI 视觉重做。
- 云存档、账号系统或联网功能。
- 全量废弃兼容字段。
- 大规模一次性数据重写。

## 5. 问题结构

### 5.1 事件生命周期层

当前事件复读不是单一冷却不足，而是多个因素叠加：

- 部分脚本模拟绕过引擎执行入口，导致 `eventHistory` 口径与真实执行不一致。
- 旧数据依赖 `triggerConditions.flags.required/not`，但运行时门禁未完整处理该语义。
- 家庭、恋爱、挫折、职业等事件缺少同类生命周期控制。
- 高权重宽年龄段事件长期保留在候选池中。

### 5.2 节奏分布层

当前节奏失衡不是单纯事件总量问题，而是正式事件池长期接管：

- formal 事件比例过高，daily 事件空间不足。
- 年龄段之间事件类别差异不够健康。
- 候选池先排序截断再抽取，可能放大高优先级事件优势。
- 家庭/职业/挫折事件在某些阶段形成体感拥堵。

### 5.3 路线主导层

路线系统存在但主导权不足：

- `routeStates` 能记录 active，但真实事件数据较少进入 locked/completed/failed。
- 事件数据缺少足够 `routeTargets`、`routeTransition` 或路线生命周期标记。
- 事件加载入口与声明入口存在不一致，部分线路内容可能没有进入主流程。
- 路线事件与通用事件之间缺少明确调度权重。

### 5.4 验证门禁层

当前验证偏工程结构，不足以证明体验健康：

- 复读率、短窗口同类密度、路线完成率、路线体感占比等指标没有成为硬门禁。
- 多样本覆盖不足，单 seed 或少量 persona 容易误判。
- warning/info 体验失败不会阻断主验证。
- 报告输出偏观察，缺少跨版本趋势和失败分类。

## 6. 分布式执行包

### 包 A：事件生命周期与复读根因治理

目标：统一事件触发历史、flag 门禁、冷却与生命周期控制，优先降低同一事件和同类事件复读。

主要验收：
- 固定 seed 下同一事件复读显著下降。
- `eventHistory` 与模拟脚本记录口径一致。
- `triggerConditions.flags` 的 required/not 语义被明确处理或明确迁移。
- 家庭、挫折、职业等关键类别有可解释生命周期边界。

### 包 B：年龄段与候选池节奏治理

目标：修正 formal/daily/storyline 分布和候选池偏置，让人生节奏有呼吸和阶段差异。

主要验收：
- formal/daily 比例回到设计区间或新的批准基线。
- 候选池不再长期被少数宽年龄高权重事件垄断。
- 各年龄段事件类别分布可解释。
- rhythm baseline 有 before/after 对比。

### 包 C：路线主导权治理

目标：让路线从“字段存在”变成“事件调度、生命周期和玩家体感的主导因素”。

主要验收：
- 至少两条核心路线可在固定样本中完成或明确失败。
- route completion 不再稳定为 0%。
- 路线事件在时间线中有连续存在。
- 线路声明与实际加载一致性得到校验。

### 包 D：体验验证门禁升级

目标：把体验健康指标纳入可执行门禁，防止结构通过但体验坏味道回归。

主要验收：
- 输出机器可读和人类可读的体验健康摘要。
- 复读、节奏、路线、家庭/恋爱至少有明确指标。
- blocker/warning/info 阈值和 waiver 规则清楚。
- 主验证或独立验证命令能稳定发现体验退化。

## 7. 推荐执行顺序

1. 包 A：事件生命周期与复读根因治理。
2. 包 B：年龄段与候选池节奏治理。
3. 包 C：路线主导权治理。
4. 包 D：体验验证门禁升级。

原因：

- A 不稳定时，B/C 的体验判断会被复读污染。
- B 不稳定时，C 的路线事件仍会被通用事件淹没。
- D 需要把 A/B/C 的稳定成果固化成长期门禁。

## 8. 风险

- 修复事件门禁可能暴露旧数据不可达问题。
- 调整候选池可能改变既有模拟基线。
- 路线接管过强可能压缩日常和家庭内容。
- 门禁升级过快可能让当前项目短期内频繁失败。
- 多会话并行若边界不清，可能重复修改同一选择逻辑。

## 9. 回滚策略

- 每个包独立提交，避免混合大改。
- 每个包保留 before/after 指标。
- 若候选池或路线调度引发大面积回归，优先回滚对应包，不回滚文档和诊断指标。
- 门禁阈值先分阶段收紧，保留有理由 waiver。

## 10. 验证策略

- 默认验证：类型检查、构建、主测试。
- 体验验证：复读复现、节奏报告、多样本真实游玩模拟。
- 报告验证：机器可读摘要和人类可读报告同时生成。
- 回归验证：固定 seed 保持可重复，新增多 persona 覆盖路线和家庭/恋爱样本。

## 11. 交付物

- 总 PRD 与 Ralph JSON。
- 多会话分发索引。
- 包 A-D 的执行包文档。
- 每包执行后的验证证据和残余风险。
