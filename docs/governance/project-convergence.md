# Wuxia-Life 项目治理与收敛方向

> 状态：治理基线
> 适用范围：当前 Wuxia-Life 主仓库
> 目的：在继续扩展产品功能之前，收敛产品模型、运行时状态、事件契约、测试体系、历史文档和代码架构，建立唯一、明确、可持续演进的项目基线。

---

## 1. 为什么需要本次治理

Wuxia-Life 已经过多轮持续开发，当前已经具备较完整的：

* 游戏运行引擎；
* 数据驱动事件系统；
* 本地与 Headless/API 运行能力；
* 自动模拟与测试体系；
* 大量事件和内容资产；
* 多阶段产品设计与实现积累。

这些积累具有价值，但长期以阶段任务和增量功能为主的开发方式，也造成了明显的模型叠加。

当前项目中同时存在：

* 多代玩家属性模型；
* 多套路线路径模型；
* 多套身份、关系和事实状态表达；
* 新旧事件格式；
* 历史兼容字段和迁移逻辑；
* 大量以开发阶段编号组织的正式运行代码；
* 已经过时但仍可能被 Agent 搜索并引用的历史设计文档；
* 固化历史需求、与当前产品规范冲突的测试。

因此，当前阶段的首要目标不再是继续增加系统、事件和玩法，而是：

> **建立唯一的产品模型，并使代码、数据、测试、文档和工具全部重新围绕这一模型收敛。**

---

# 2. 权威信息层级

项目中的信息必须存在明确的权威层级。

发生冲突时，高层级规则覆盖低层级规则。

## 2.1 第一层：当前产品规范

当前明确指定为权威产品规范的文档，例如：

```text
docs/product/player-model.md
```

这类文档定义：

* 玩家是什么；
* 核心概念是什么；
* 概念之间的边界；
* 哪些旧概念已经废弃。

产品语义以此为最高依据。

代码、测试和旧文档不得反向证明已经废弃的产品设计仍然有效。

---

## 2.2 第二层：项目治理规范

例如本文档。

治理规范定义：

* 如何处理新旧模型冲突；
* 如何迁移；
* 如何删除历史资产；
* 如何判断测试是否仍然有效；
* 如何控制项目范围；
* Agent 应遵守什么开发原则。

治理规范不得重新定义具体产品语义。

---

## 2.3 第三层：当前有效工程契约

包括经过明确确认仍然生效的：

* API Contract；
* Save/Snapshot Contract；
* Event Contract；
* Runtime Contract；
* 数据 Schema；
* 关键工程 ADR。

只有被当前文档索引明确列为有效的工程契约，才具有权威性。

---

## 2.4 第四层：代码与测试

代码和测试代表：

> 当前项目实际实现了什么。

它们不天然代表：

> 当前产品应该是什么。

当代码或测试与更高层级产品规范冲突时，应修改或删除代码和测试，而不是为了让旧测试继续通过而保留废弃模型。

---

## 2.5 第五层：历史文档和阶段产物

包括但不限于：

* 旧 PRD；
* Phase/Pxx 设计稿；
* 阶段总结；
* 测试报告；
* closure/proof/baseline 文档；
* 旧实现计划；
* 已被新规范替代的设计说明。

这些内容只能作为 Git 历史参考。

除非被重新审核并提升为当前有效文档，否则：

> **不得作为新开发的需求来源。**

---

# 3. 当前治理目标

本轮治理最终要建立五个“唯一”。

## 3.1 唯一玩家模型

玩家的长期核心状态只能存在一套正式表达。

当前以 `docs/product/player-model.md` 为产品依据。

核心概念应明确划分为：

```text
投入
属性
资源
特质
状态
事实
```

不同类型的信息不得因为实现方便而重复创建平行字段。

---

## 3.2 唯一事实来源

同一个产品概念不得长期存在多套彼此同步的状态。

例如应避免：

```text
routeStates
roadCommitments
routeHistory
lifePath.focus
route_* flags
```

同时表达同一类路线事实。

也应避免身份、关系、成就、事件事实分别存在多套平行状态。

每个领域必须最终确定：

> Single Source of Truth

其他表达只能是：

* 派生值；
* ViewModel；
* 临时计算结果；
* 明确版本化的兼容边界。

不得成为第二套永久状态。

---

## 3.3 唯一事件契约

所有正式事件最终必须遵守同一套：

* Condition Schema；
* Effect Schema；
* Choice Schema；
* Fact/State 引用规则。

不得长期维持：

```text
legacy
target
mixed
```

三套格式共存。

---

## 3.4 唯一有效测试基线

测试必须验证：

> 当前产品契约和当前工程契约。

不得仅因为某个历史测试已经存在，就将其视为必须保留的产品行为。

与当前权威规范冲突的测试：

* 修改；
* 重写；
* 删除；

不得通过恢复旧概念使其重新通过。

---

## 3.5 唯一当前文档入口

Agent 不应自行从数百份历史文档中判断哪份需求最新。

必须建立少量明确入口，例如：

```text
AGENTS.md
docs/README.md
docs/product/player-model.md
docs/governance/project-convergence.md
```

`docs/README.md` 应维护：

> 当前真正有效文档的有限索引。

未被索引的历史文档默认不具有规范效力。

---

# 4. 本轮治理明确不做什么

治理期间严格控制范围。

除非是完成模型迁移所必需，否则暂不进行：

* 新大型玩法系统；
* 新路线体系；
* 新核心属性；
* 新长期资源体系；
* NPC 好感等大型关系系统扩展；
* 大规模新增事件；
* 大规模 UI 重做；
* 为未来假设需求提前设计抽象层；
* 为旧模型继续增加兼容能力。

本轮治理的判断标准不是：

> “还能增加什么？”

而是：

> “什么可以删除、合并，并成为唯一模型？”

---

# 5. 核心治理原则

## 5.1 收敛优先于兼容

当新规范明确废弃旧模型时，默认策略应为：

```text
迁移
→ 删除旧模型
```

而不是：

```text
新增新模型
→ 保留旧模型
→ 写 bridge
→ 双向同步
→ 永久兼容
```

只有存在明确、仍然有效的外部兼容义务时，才能保留版本化兼容边界。

兼容必须有：

* 明确对象；
* 明确原因；
* 明确生命周期；
* 明确删除条件。

不得存在无期限的“保险式兼容”。

---

## 5.2 语义迁移，不做机械字段替换

旧概念不得仅通过批量 rename 强行映射到新模型。

例如：

```text
外功
内功
轻功
```

不一定全部简单变成：

```text
功力
```

其中某些语义可能应表达为：

* 功力；
* 功法；
* 特质；
* 状态；
* 故事事实。

类似地：

```text
悟性
魅力
经营
影响力
健康
精力
```

都必须根据具体产品语义判断归属。

迁移原则是：

> 保留真正需要表达的语义，而不是保留旧字段。

---

## 5.3 类型系统应该帮助暴露问题

当一个旧核心字段已经被明确废弃时，优先考虑从权威类型中删除。

让 TypeScript、测试和构建主动暴露所有依赖点。

不应大量使用：

```ts
deprecatedField?: number
```

长期隐藏尚未完成的迁移。

对于核心模型迁移：

> 编译错误是一种迁移清单，而不是需要规避的问题。

---

## 5.4 删除优于 Deprecated 堆积

Git 已经保存历史。

明确废弃且无当前价值的：

* 文档；
* 测试；
* 报告；
* 类型；
* Bridge；
* Legacy Adapter；
* Feature Slice；

原则上应删除。

不要因为：

> “以后也许有用”

而永久保留。

需要恢复时，可以从 Git 历史获取。

---

## 5.5 不以阶段编号作为长期架构

类似：

```text
p11/
p16/
p17/
p20/
p44/
p50/
```

只能代表开发历史，不应成为稳定的业务领域边界。

仍然有效的逻辑最终应迁移到稳定领域，例如：

```text
player/
progression/
identity/
relations/
events/
scheduling/
narrative/
ending/
```

阶段编号不应继续向正式运行时架构扩散。

---

## 5.6 不在模型尚未稳定时做大规模架构美化

治理顺序必须是：

```text
产品模型
→ 状态模型
→ 运行行为
→ 数据
→ 测试
→ 文档
→ 架构整理
```

不得首先进行：

* 大规模目录重命名；
* 抽象接口重构；
* Service 拆分；
* God Object 美化；

然后才处理产品模型。

否则只是把旧模型重新整理得更漂亮。

---

# 6. 当前已识别的重点冲突

以下内容作为当前治理的重点检查对象。

具体影响面仍需要通过代码审计确认，不应仅依据本文直接批量修改。

---

## 6.1 四项投入模型

当前产品定义中的四项投入：

```text
武道
经世
仕途
隐逸
```

其本质是：

> 人生时间和精力长期投入方向。

它们：

* 可以同时发展；
* 不区分主路线和次路线；
* 不限制最多发展几项；
* 不存在加入、退出、承诺、证明、锁定、完成或失败。

因此当前运行时中涉及以下语义的模型需要重新审核：

```text
roadCommitments
primary/secondary road
locked_in
completed
proofCount
commitRoad
recordRoadProof
completeRoad
route lifecycle
路线互斥
路线锁定
```

不得默认保留。

---

## 6.2 六项核心属性

当前核心属性：

```text
功力
体魄
学识
人脉
名望
侠义声誉
```

以下历史数值必须重新进行语义分类：

```text
外功
内功
轻功
悟性
魅力
经营能力
影响力
健康
精力
其他遗留成长值
```

处理方式可能包括：

```text
合并到核心属性
转为特质
转为状态
转为资源
转为事实
转为具体功法/身份信息
直接删除
```

不得创建第二套“辅助长期属性体系”。

---

## 6.3 身份、关系和事实状态

当前需要审查是否存在同一概念多套状态来源的问题。

重点包括：

```text
identity
lifePath
player fields
flags
relationships
achievements
events
triggeredEvents
eventHistory
route history
```

目标是明确：

```text
写入源
派生源
展示层
历史记录
```

之间的边界。

---

# 7. 分阶段治理方案

本轮治理不得以“一次性全仓重构”的方式实施。

采用阶段式硬收敛。

---

## Phase 0：建立可信工程基线

目标：

> 后续所有迁移都建立在真实可验证的工程反馈上。

需要完成：

### 0.1 修正 TypeScript 检查入口

确保：

```text
typecheck
```

真正覆盖正式项目，而不是出现“typecheck 通过但 build 存在大量 TS 错误”的假绿状态。

---

### 0.2 建立分层验证命令

至少区分：

```text
快速静态检查
核心单元测试
模型契约测试
事件数据校验
集成测试
完整模拟/体验 Gate
```

日常小修改不得必须运行耗时极长的完整人生模拟才能获得第一轮反馈。

---

### 0.3 记录治理开始时的真实基线

记录：

* build 状态；
* typecheck 状态；
* 测试状态；
* 事件校验状态；
* 已知 blocker。

基线用于判断治理是否改善，而不是要求所有历史错误在 Phase 0 一次解决。

---

## Phase 1：建立 Canonical Player State

这是本轮治理最重要的阶段。

目标：

> 在代码层建立唯一玩家模型。

首先解决：

```text
PlayerState
GameState
初始化状态
序列化状态
```

明确：

```text
投入
属性
资源
特质
状态
事实
```

分别由什么结构承载。

禁止在此阶段继续增加新的平行兼容模型。

---

## Phase 2：迁移核心运行行为

基于新的 Canonical Player State，依次迁移：

```text
Condition Evaluator
Effect Executor
主动行动
成长逻辑
路线/投入逻辑
身份逻辑
状态变化
资源变化
```

原则：

每迁移一个领域：

```text
接入新模型
→ 迁移有效语义
→ 删除旧写入路径
→ 删除旧字段
→ 更新对应测试
```

不要先把整个项目全部桥接到新旧双模型，再统一删除。

---

## Phase 3：迁移内容和事件资产

只有核心运行语义稳定后，才集中治理事件。

目标：

```text
legacy/mixed
→ canonical event contract
```

对事件中的旧属性、旧路线和旧 effect：

必须逐类定义语义迁移规则。

禁止纯字符串全局替换。

优先处理：

```text
blocker
→ 高频核心事件
→ 主人生路径事件
→ 其他普通事件
```

---

## Phase 4：迁移存档、Headless、API 和 UI

当核心状态与事件模型稳定后，再迁移：

```text
Snapshot
Save/Load
Replay
Headless runtime
API DTO
UI ViewModel
人生总结
结局展示
```

UI 不应再直接决定产品状态结构。

展示层应消费 Canonical State 或明确的派生 ViewModel。

---

## Phase 5：清理历史资产和架构

完成产品模型迁移后：

### 删除

* 废弃字段；
* Legacy Bridge；
* 已无用途 Migration；
* 冲突测试；
* 历史测试报告；
* 阶段 closure/proof 文档；
* 被新规范完全替代的旧设计稿；
* 不再使用的 Phase 代码。

### 重组

将仍然有效的：

```text
pXX
phaseXX
```

逻辑迁移回稳定业务领域。

### 最后再处理

大型类和 God Object 的架构拆分。

---

# 8. 文档治理规则

## 8.1 `docs/README.md` 作为唯一入口

它只索引：

> 当前开发真正需要阅读的少量文档。

不要试图索引全部历史文件。

---

## 8.2 历史报告不进入 docs

自动生成内容默认进入：

```text
artifacts/
tmp/
.gitignored reports/
```

不再持续提交：

```text
docs/test-reports/
```

---

## 8.3 冲突旧文档原则上删除

当旧文档：

* 已被新规范完整替代；
* 明确存在产品语义冲突；
* 不再承担当前工程契约作用；

应从当前分支删除。

Git History 即为 archive。

---

## 8.4 新文档必须回答一个问题

创建文档前必须明确：

> 这份文档未来由谁读取，用来做什么决策？

无法回答时，不创建。

避免再次产生：

```text
plan
summary
report
analysis
closure
proof
final-final
final-v2
```

型文档堆积。

---

# 9. 测试治理规则

测试分为三类。

## A. 当前契约测试

验证当前明确规范。

必须保留并维护。

---

## B. 行为回归测试

验证仍然需要的实际游戏行为。

经审核后保留。

---

## C. 历史需求验收测试

例如仅为了证明某个 Pxx 任务当时完成而存在的测试。

如果其行为已经：

* 被新规范替代；
* 不再是当前产品要求；
* 与当前模型冲突；

应修改或删除。

测试文件存在本身不构成产品需求。

---

# 10. Agent 开发规则

任何 AI Agent 在进行治理任务时必须遵守以下流程。

## 10.1 先读权威文档

至少：

```text
AGENTS.md
docs/README.md
docs/product/player-model.md
docs/governance/project-convergence.md
```

---

## 10.2 不自行扩展产品需求

发现语义缺口时：

```text
记录问题
→ 给出证据和选项
→ 等待产品裁决
```

不得为了让代码“完整”而自行增加：

* 新属性；
* 新路线机制；
* 新状态；
* 新兼容模型。

---

## 10.3 审计和实施分离

复杂迁移必须先进行：

> Read-only impact analysis

输出：

* 旧概念定义位置；
* 读路径；
* 写路径；
* UI 使用；
* 数据资产使用；
* 测试依赖；
* 存档/API 影响；
* 推荐迁移顺序。

完成审查后才能进入实施。

---

## 10.4 每次实施范围必须可验证

一个治理任务应尽量满足：

```text
单一领域
明确输入
明确删除目标
明确测试
明确 Done Definition
```

避免：

> “按照新模型重构整个项目”

这种无限范围任务。

---

## 10.5 不隐藏未解决问题

Agent 完成任务时必须明确报告：

```text
改了什么
删了什么
哪些测试通过
哪些测试未运行
哪些失败是原有问题
新增了什么临时兼容
还有哪些未迁移点
```

禁止以：

> “核心功能已完成”

代替具体证据。

---

# 11. 每阶段的完成定义

一个阶段只有同时满足以下条件才算完成：

### 产品

* 与当前权威规范一致。

### 类型

# 13. 当前阶段最高原则

在本轮治理完成之前：

> 不以增加系统数量衡量开发进度。

主要衡量指标应改为：

```text
删除了多少重复概念
减少了多少状态来源
统一了多少数据契约
删除了多少无效兼容
降低了多少 Agent 判断歧义
让多少规则真正只有一个答案
```

Wuxia-Life 当前已经拥有足够多的系统和内容来证明架构能力。

下一阶段真正需要证明的是：

> **这个项目能否从长期增量开发形成的复杂历史中，重新收敛为一个清晰、一致、可持续演进的游戏模型。**

在模型重新统一之前，克制扩展本身就是最重要的开发工作。
