# Character / Relationship Product Contract v1

> 状态：Accepted product contract
>
> Human accepted：2026-08-30
>
> 本文位于 `docs/product/player-model.md` 之下，定义 Wuxia-Life 重要人物与人物关系领域的正式产品语义。本文不替代第一层玩家模型，也不授权本轮直接修改 Runtime、Event Schema、PlayerState、Snapshot 或现有事件内容。
>
> 当前 repository implementation 仍存在与本文冲突的 legacy romance / relationship semantics。它们属于 **pending migration implementation reality**，不得反向覆盖本文 authority。

## 1. 产品问题与治理目标

当前感情内容的主要问题不是事件数量不足，而是人物与关系被过早压缩成一条预设剧情：固定人物进入、初遇直接开启爱情、关系依赖抽象进度或好感、随后在固定年龄段收束到婚姻。

本 Contract 重新定义：

1. 一个具体人物如何合理进入玩家人生；
2. 玩家如何通过持续经历认识这个人；
3. 关系如何由具体事实、选择与冲突形成；
4. 恋爱、婚姻、友情、合作、疏远等关系如何保持语义分离；
5. 重要人物如何在后续人生中保持连续性；
6. 哪些能力应该共享，哪些内容必须保持人物专属。

核心产品模型为：

```text
玩家既有人生
↓
某个具体人物因合理原因进入生活
↓
认识 / 再次交集 / 共同经历 / 冲突
↓
形成可解释的历史与 durable facts
↓
在具备真实前史时出现关系发展的可能
↓
玩家决定关系如何继续
↓
人物作为世界中的具体人物继续影响后续人生
```

**感情不是一条独立任务线，而是人物关系在人生中的一种可能发展结果。**

## 2. Person-first：人物首先是人物

重要人物首先是世界中的具体人物，不是：

- 恋爱候选槽位；
- 配偶候选；
- 攻略对象；
- 为触发某条关系线临时投放的功能角色。

一个人物可以在具体内容支持下形成：

- 熟人；
- 友情；
- 合作；
- 冲突；
- 暧昧或未明确的重要关系；
- 恋爱；
- 分离；
- 婚姻；
- 其他具有明确内容依据的关系。

没有发展成爱情不意味着人物内容失败，也不意味着人物必须从后续人生中消失。

## 3. Person Access：人物如何进入玩家人生

人物进入玩家人生必须存在合理、可解释的接触来源，但**不要求所有人物绑定特定人生路线**。

允许至少两类入口：

### 3.1 普适型人物

多种人生都可能自然接触，例如：

- 市集与地方生活；
- 公共事务；
- 旅途；
- 地域性事件；
- 其他不依赖特定路线的社会环境。

### 3.2 路径关联型人物

因玩家具体人生环境产生接触，例如：

- 商路；
- 门派；
- 仕途；
- 江湖事务；
- 家庭关系；
- 其他已存在的人生事实。

人物不需要覆盖所有入口。不得为了保证某个 NPC 每局出现，而人为给其补充大量无关入口。

**玩家一生没有认识某个具体人物，是合法的人生差异。**

## 4. 相遇、关系、恋爱、婚姻必须分离

以下概念不得互相替代：

```text
相遇
≠
认识
≠
了解 / 关系深化
≠
恋爱
≠
婚姻
≠
家庭
```

一次相遇不得自动证明：

- 心动；
- 真爱；
- 爱情已经开始；
- 双方互有感情；
- 该人物是婚姻候选；
- relationship progression 已经推进。

关系应通过持续接触、共同经历、具体选择、价值冲突、承诺、分离等事实逐渐成立。

## 5. Fact-first：关系由发生过的事情构成

继承 `player-model`：**不建设通用 NPC 好感度或关系数值系统。**

关系演化优先记录可解释的具体事实，例如：

- 与某人共同经历过某件事；
- 某人在危难时帮助过玩家；
- 玩家曾经失信于某人；
- 双方在重要价值问题上发生过冲突；
- 双方曾作出明确承诺；
- 双方因现实选择而分离；
- 双方明确建立了某种重要关系。

禁止把下列抽象投影重新做成关系真相：

- affinity 0～100；
- trust score；
- closeness score；
- romance progress；
- relationship XP；
- marriage quality score；
- 其他隐藏 relationship progression 数值。

核心判断不是“关系推进了多少”，而是：

> **两个人过去具体发生过什么，为什么现在会处于这样的关系。**

## 6. 状态最小化：History / Durable Fact / Current Condition

人物内容应区分三类信息：

### 6.1 History

表示某件事情发生过。

普通过去经历优先由 Event History 等现有历史机制表达，不为纯回顾或纯文本差异新增持久业务状态。

### 6.2 Durable Fact

表示某件事情对未来持续成立，并且未来内容确实需要消费。

只有满足以下测试的信息才应成为 durable state：

> 如果未来事件不知道这件事，会不会无法正确理解当前人物关系或世界事实？

答案为“否”时，不新增 durable state。

### 6.3 Current Condition

表示暂时处境，例如某次冲突后的短期疏远。临时处境不得因为实现方便被永久升级成人生事实。

第一阶段不建立统一 `relationshipStage` state machine。

## 7. No hidden攻略：事实不能变成拆散的好感度

多个 boolean、event history 或 facts 不得机械组合成隐藏 affinity。

禁止：

```text
事件 1 选择“正确答案”
+ 事件 2 选择“正确答案”
+ 事件 3 选择“正确答案”
→ romance threshold reached
```

过去事实只用于：

- 建立叙事资格；
- 体现不同前史；
- 使后续人物反应和选择具有因果。

只要叙事上成立，彼此契合、经历过争执、曾经意见不同等不同前史都可以通向进一步关系。不得把人物关系设计成单一攻略答案。

## 8. 玩家决定私人关系，不由作者预先排名

系统可以呈现人物、处境、他人的态度和选择后果，但不得默认替玩家宣布：

- 某人是“真正的真爱”；
- 没选某人是一生遗憾；
- 某一种婚姻天然优于另一种；
- 结婚或生子代表私人生活成功；
- 没有完成某条 romance arc 代表人生失败。

单身、未婚、错过、分离、没有子女等均可以是完整合法人生。

“遗憾”等强情感评价只有在已有充分人生前史时才可以成立，例如长期共同经历、明确承诺、主动放弃以及后续重新面对该选择。系统不得凭空替玩家制造情感历史。

## 9. 恋爱与婚姻 Contract

恋爱不是婚姻的自动前置流程，婚姻也不是爱情剧情的完成状态。

产品模型必须允许：

- 恋爱而不婚；
- 相爱但最终分离；
- 婚后才逐渐建立深厚感情；
- 认识后判断不适合成婚；
- 一生不婚；
- 更晚的人生阶段才形成重要关系。

年龄、家庭和社会环境可以使婚姻议题更可能出现，但不得把已有恋爱状态自动收束到固定年龄婚姻 resolution。

家族介绍或安排婚姻可以存在，但其首先意味着：

> **玩家因此认识一个具体人物，并面对真实婚姻选择。**

它不得被预先定义为次等婚姻；关系质量应由后续实际经历产生。

## 10. 重要人物的长期连续性

重要人物进入玩家人生以后，应能够作为同一个具体人物被后续内容稳定引用。

人物越重要，越应该在理应受其影响的重大人生节点保持存在感，例如：

- 家族；
- 事业；
- 商业；
- 仕途；
- 门派；
- 江湖冲突；
- 生死危机；
- 婚姻与家庭；
- 隐退；
- 人生回响。

不要求高频出现，也不要求完整模拟人物一生。

长期影响优先通过以下内容表现：

- 新事件；
- 新选择；
- 新责任；
- 新风险；
- 新社会关系；
- 对既有事件的不同参与；
- 后续人生回响。

属性变化仍可作为具体事件的自然结果，但不得把重要人物主要设计成永久 buff 或装备式加成。

## 11. Person Definition Contract v1

Person Definition Contract v1 首先是**内容设计 / authoring Contract**，不等于新增 Runtime Schema。

一个达到“重要人物”级别的 NPC，原则上只需要回答以下八类问题。

### 11.1 Identity

这个人基本是谁：

- 稳定 identity；
- 固定人物或可实例化人物原型；
- 名称固定或由原型实例化；
- 性别固定或允许变化；
- 当前内容真正需要知道的基础社会身份。

不要求人物百科。

### 11.2 Access

玩家为什么有机会认识这个人。可以是普适型入口，也可以是路径关联型入口。

### 11.3 Character Anchors

只定义足以让人物在不同事件中保持一致的少量稳定锚点，通常包括：

- 这个人重视什么；
- 一个明显的做事方式或性格特征；
- 一个对其人生有实际影响的现实约束。

一般只需要 2～3 个当前内容真正使用的锚点，不建设人格参数矩阵。

### 11.4 Core Concern

定义这个人物自己的故事主要围绕什么问题、责任或矛盾展开。

人物自己的核心 concern 应当在不发生恋爱时仍然成立，避免把人物写成“专门陪玩家谈恋爱的人”。

### 11.5 Event Responsibilities

定义人物内容需要承担哪些职责，例如：

- 进入玩家人生；
- 再次出现并体现人物连续性；
- 展示人物特征；
- 发生一次具有后果的共同经历或冲突；
- 让过去事实影响后续；
- 在必要时产生长期回响。

这是职责列表，不是固定事件数量、统一剧情流程或关系状态机。

### 11.6 Durable Facts

只定义后续内容真正必须读取的少量事实。人物专属事实可以保持人物专属，不要求所有人物共享一套字段。

### 11.7 Relationship Possibilities

只声明当前内容真正支持的关系可能性。

某个人物可以支持友情、恋爱、疏远等；另一个人物可以只支持合作与友情。不得要求所有人物覆盖所有关系类型。

### 11.8 Long-term Hooks

只定义当前已有内容依据的少量后续入口。不得为了“人物完整”提前设计其几十年完整人生。

## 12. Shared vs character-specific

正式原则：

> **共享人物设计 Contract 和最小运行原语；不共享统一人物剧情流程。**

共享层只应承担真正稳定、跨人物需要的最小能力，例如：

- 稳定引用一个 concrete person；
- 知道相关历史是否发生；
- 保存后续真正需要的 durable facts；
- 后续事件读取这些事实。

人物自己的以下内容默认保持专属：

- 人物设定；
- 核心 concern；
- 事件；
- 故事事实；
- 关系路径；
- 后续 hook。

故事事实人物专属不是架构缺陷。不得因为字段名称相似就抽成通用类型或数值。

### 12.1 Shared semantic promotion rule

只有满足以下至少一种情况，才重新判断是否将人物专属语义提升为 shared canonical capability：

1. 两个以上独立人物真实需要同一稳定语义；
2. 婚姻、家庭等另一个独立产品域必须统一消费该语义；
3. 不共享会导致正式事实无法可靠表达，而不只是出现少量重复；
4. 该共享语义能够用一句稳定的产品语言解释，且不依赖某一个人物剧情。

即使发生提升，也只抽最小稳定语义，不因此连带建设 affinity、trust、stage、quality 等其他字段。

## 13. 固定人物与实例化人物正交

人物可以来自：

```text
固定人物
```

也可以来自：

```text
人物原型
→ 运行时实例化
→ concrete person
```

对 Character / Relationship consumer 而言，两者都只是：

> **已经存在并具有稳定 identity 的 concrete person。**

人物关系内容不得依赖该 identity 的生成过程。

**Generic Person Instantiation 仍未授权。** 有限 Sex-Variant Person Archetype 能力由 PD-103 / Sex-Variant Person Archetype Contract v1 独立治理；该能力不授权 generator、prototype runtime schema、姓名/性别生成、亲属身份实例化算法或 generic NPC framework。

## 14. 人物原型可以拥有专属内容

支持运行时实例化不意味着事件也必须泛化生成。

人物或人物原型可以拥有自己的：

- 初识事件；
- 核心矛盾；
- 共同经历；
- 关系选择；
- 后续内容。

禁止为了减少事件数量而建设：

- 万能初遇模板；
- 万能人物冲突事件；
- 万能恋爱事件；
- procedural romance story generator。

事件首先服务人物和故事真实性；实例化只允许改变不破坏这些事件语义的属性。

姓名通常比性别、家庭位置、社会身份更容易变化。若某个可变维度会迫使大量事件出现特殊分支，应优先收缩人物原型，而不是扩大生成组合空间。

## 15. Anti-overdesign Guard

单个人物的设计如果开始要求新增以下内容，应先停止并判断这是共享产品缺口还是人物过度设计：

- 通用人格参数；
- 通用关系阶段；
- 新的好感度 / 信任度 / 亲密度维度；
- NPC autonomous simulation；
- 为所有人物强制增加大量统一字段；
- 全部人物 × 全部关系类型组合矩阵；
- 全部玩家性别 × NPC 性别剧情矩阵；
- 为一个人物修改大量无关系统。

在没有第二个独立真实需求前，默认不抽共享能力。

人物只需要拥有**足以支撑当前内容的人物性**，不追求完整人格模拟、完整家谱或完整人生传记。

## 16. 明月人物纵切 v1

明月人物纵切 v1 是本 Contract 的第一验证样板，不是新的标准恋爱攻略模板。

### 16.1 Accepted boundary

- 明月可以继续作为固定人物；
- 明月可以作为普适型人物，不要求绑定某一人生路线；
- 当前市集相遇可以保留作为人物入口；
- 市集相遇本身不是问题，旧语义把初遇直接升级为爱情才是问题；
- 第一纵切不使用人物实例化作为前置依赖；
- 明月首先作为人物存在，恋爱只是可能关系之一。

### 16.2 最小事件职责

第一纵切只验证以下职责：

```text
市集初识
↓
再次交集
↓
人物塑造 / 共同经历
↓
一次有实际后果的价值冲突或重要选择
↓
在具备真实前史后出现关系性质选择
├─ 进一步发展感情
└─ 不发展为恋爱关系
↓
至少一次后续人生回响
```

这不是所有人物必须复制的固定剧情流程。

不发展爱情必须是完整、正常的关系结果，明月仍可以作为朋友、故交、合作对象或其他由具体内容支持的身份继续存在。

### 16.3 v1 明确不要求

第一纵切不要求同时完成：

- 婚姻；
- 子女；
- 中年婚姻危机；
- 晚年完整剧情；
- 完整明月家族史；
- 完整人物传记；
- 全部现有明月事件迁移。

现有共同任务、家族约束、价值冲突等母题可以在迁移时重新利用；是否保留具体事件由后续 migration design 决定。

## 17. 明月 v1 的最小关系事实

第一纵切优先利用具体事件历史和人物专属 facts，不提前建立 shared canonical romantic relationship schema。

产品上需要表达的最小信息预计包括：

- 玩家已经认识明月；
- 一两个后续真正需要消费的重要共同经历 / 选择；
- 玩家与明月是否明确建立了感情关系。

“没有发展爱情”原则上不需要为了对称而永久保存一个反向状态。只有后续内容确实需要区分“明确拒绝”与“从未进入该选择”时，相关选择才成为必要历史或 fact。

明月 v1 不读取或写入 affinity 作为关系推进依据，也不通过多个 boolean 模拟 romance score。

如果第二个独立人物或婚姻域未来需要统一读取“与某 concrete person 存在 confirmed romantic relationship”，再按 §12.1 promotion rule 判断是否提升为 shared canonical semantic。

## 18. Legacy product semantics retirement boundary

以下 current semantics 与本 Contract 冲突，正式降级为：

> **legacy product semantics pending migration**

包括：

- `love_started` 作为统一爱情总开关；
- 初遇直接进入爱情；
- 固定 `lover_mingyue` 作为所有玩家的默认恋爱对象；
- affinity 驱动关系推进；
- 当前 `family_marriage` 的“真爱 / 家族安排 / 自由恋爱”价值排序；
- `marry_mingyue` 作为 preferred romance choice；
- spouse / children 作为 romance achievement；
- `marriage_quality_*` 一类统一婚姻质量评分；
- 恋爱状态自动推动固定年龄婚姻收束；
- 明月作为 canonical 唯一真爱路线。

**Retirement 表示旧产品语义退出 authority，不表示本次 authority closure 已经删除或迁移 Runtime / events / tests。**

现有内容中的共同任务、家庭约束、价值冲突、分离、重逢、危机等故事母题，可以在未来迁移时重新判断；不得因为旧文件存在就自动恢复为 current product authority。

## 19. 与 Family Domain 的边界

本 Contract 只定义人物关系与婚姻之间的正确语义边界，不在本轮重新设计完整 Family Domain。

当前不自动扩大到：

- 生育系统；
- 子女成长；
- 子女教育；
- 子女婚姻；
- 孙辈；
- 家风；
- 完整家庭生命周期；
- inheritance system。

旧家庭内容如果依赖已经退休的 romance / marriage premise，应在后续 migration design 中解除错误依赖，但不得借此顺便重做整个家庭域。

## 20. Non-goals

当前明确不建设：

- 通用 NPC simulation；
- 通用 NPC AI；
- NPC 自主行动世界模拟；
- 通用好感度、信任度、亲密度或 relationship XP；
- relationship stage machine；
- marriage quality 数值；
- 全局性取向数值 / 模拟系统；
- procedural romance story generator；
- 万能人物 / 恋爱事件模板；
- 一次性设计全部人物；
- 一次性恢复 historical mature-love / marriage-conflict backlog；
- 完整婚姻危机模拟；
- 完整家庭生命周期重做；
- 人物实例化 Runtime / generator。

## 21. 第一纵切成功标准

明月人物纵切 v1 后续真正实施时，至少应证明：

1. 明月因合理人生事件进入玩家生活；
2. 初遇没有自动产生爱情；
3. 玩家通过持续内容真正认识这个人物；
4. 至少一个共同经历或重要选择影响后续内容；
5. 关系发展的选择只在具有足够前史时出现；
6. 玩家可以发展感情，也可以不发展感情；
7. 两个结果都继续产生合理人生，而不是成功 / 失败二分；
8. 至少一个较晚节点真实读取前史并产生不同回响。

成功不再以“娶明月”“拥有 spouse / children”或 romance arc completion 衡量。

## 22. Authority 与当前 implementation 状态

本文自 2026-08-30 起是 `player-model` 之下的 accepted Character / Relationship product authority。

当前 implementation 中与本文冲突的旧 romance / relationship semantics 仍可能物理存在。后续必须通过独立 migration decomposition 与 implementation tasks 处理。

在 migration closure 之前：

- 旧实现只能描述 implementation reality；
- 旧实现和旧测试不能反向提升为产品 authority；
- 新人物 / 关系工作不得新增对 legacy affinity / love progression 语义的依赖；
- 不得为了兼容旧模型而在新旧语义之间建立长期双轨或兼容层。
