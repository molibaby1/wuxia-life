# 当前项目现状问题描述

## 1. 文档目的

本文档用于描述项目在当前阶段的真实问题状态，供后续新会话继续分析、规划和制定修改方案。

本文档只描述现状、表现、影响和证据，不预设具体实现方案，不替后续会话做技术路线决策。

## 2. 当前结论摘要

项目目前处于一种“结构治理已推进、核心体验问题仍然明显”的状态。

已经完成的事项包括：

- P2 相关的玩法结构工作已经形成代码、测试和文档证据。
- 生产构建、类型检查、主测试命令当前可通过。
- 结构化选择反馈、路线/身份规则、存档主流程、P2 收口文档均已存在。

但项目的主要矛盾仍然没有转移：

- 游戏核心体验仍然表现出明显的事件复读和节奏失衡。
- 自动化验证可以证明“代码能跑”，但不能证明“人生模拟体验健康”。
- 工程侧的可靠性和结构比之前更好，但玩家侧的感受仍然容易掉回“事件表格重复播放”的印象。

## 3. 问题背景

项目在前几个阶段已经完成了较多结构性工作，包括：

- 事件系统治理
- 条件表达式治理
- 反馈闭环建设
- 路线与身份规则整理
- 存档系统接入
- P2 相关 PRD、测试报告、closure 文档补齐

这些工作提高了项目的可维护性、可验证性和结构清晰度，但没有自动消解事件内容和节奏层面的老问题。

换句话说，项目现在的问题不再是“代码完全不可控”，而是“代码逐渐可控了，但体验仍然不够好”。

## 4. 现状主要问题

### 问题一：事件复读仍然明显

当前模拟结果中，仍然可以观察到同类事件或同一事件在相邻年龄段反复出现。

典型表现包括：

- 童年阶段连续多年触发“意外受伤”
- 青年阶段连续多年触发“大病一场”
- 成年阶段多次重复出现“喜结良缘”或同类家庭事件
- 某些阶段被少数高权重事件反复占据，导致人生轨迹显得机械

这个问题说明：

- 事件选择系统虽然经过了结构化治理，但在体验上仍未有效打散重复
- 冷却、权重、剧情线密度、同类事件分布之间的组合效果仍不足以防止复读
- 人生模拟的“变化感”依然偏弱

影响：

- 玩家容易感到体验单调
- 剧情表现缺少命运推进感
- 路线系统的存在感会被重复事件噪音稀释

## 5. 当前验证结果与问题的矛盾

项目当前的主验证命令可以通过：

- 类型检查通过
- 生产构建通过
- 主测试通过

但这与体验问题并不矛盾。

现阶段自动化验证主要证明的是：

- 类型和模块关系没有炸
- 核心命令链路可运行
- 一部分结构性行为符合预期
- P2 收口项有代码和测试证据

这些验证还不足以证明：

- 事件分布是否足够多样
- 路线推进是否足够自然
- 家庭、恋爱、挫折、成长等内容是否形成合理节奏
- 玩家是否会觉得每局人生有明显差异

当前项目的一个关键现象是：

**“测试通过”已经不能直接代表“体验健康”。**

## 6. 结构治理与体验治理的错位

目前项目已经完成了不少结构性工作，例如：

- 结构化选择反馈
- 路线/身份互斥规则
- 存档版本边界
- 条件表达式白名单解析
- P2 收口文档与补充说明

这些工作让项目更容易维护，也更适合继续演进。

但核心体验问题仍然集中在：

- 重复事件
- 节奏失衡
- 路线可感知度不足
- 玩家选择的长期差异感仍不够强

这意味着项目现在进入了一个新的阶段：

后续工作的重点，不再是继续补齐结构性“有没有”，而是要回答体验层面的“好不好”。

## 7. 条件表达式系统的当前边界

条件表达式系统已经从宽松执行转向更严格的受控解析。

这一变化的正面效果是：

- 风险更可控
- 表达式能力边界更清楚
- 不再依赖不安全的执行方式

但它也带来一个现实边界：

- 旧数据如果依赖超出白名单能力的表达式，就必须被迁移、重写或明确废弃

当前已知情况是：

- 先前依赖 `Math.random()` 的旧条件已经被收尾文档点名处理
- 测试日志中仍会出现一批表达式被拒绝的输出

这说明表达式系统本身并非失控，但“表达式能力边界”和“事件数据写法边界”的关系，仍需要后续会话持续保持清晰认知。

这个问题当前不是最主要的体验矛盾，但它会持续影响内容扩展方式。

## 8. 路线系统已存在，但体验主导权仍不充分

P2 之后，路线和身份相关结构已经进入主流程：

- 路线变化可以在反馈中展示
- 路线/身份互斥已有规则化表达
- 路线相关字段和文档证据已经齐备

但从当前模拟表现看，路线系统虽然“存在”，却未必已经“主导体验”。

如果玩家在大量重复事件和通用事件中穿行，路线系统就容易退化为：

- 某些状态字段在变
- 某些规则在起作用
- 但玩家体感上并没有明显进入某条独特的人生轨迹

也就是说，路线系统的结构完成度，不等于路线体验的完成度。

## 9. 存档系统当前状态

存档系统目前处于“工程上基本成立”的状态。

已知正向事实：

- 存档版本标记和兼容边界存在
- 主流程中已有保存和读取入口
- 浏览器构建兼容性问题已经通过去除 Node 静态依赖处理
- P2 收口补充文档已记录相关处理

当前没有明显证据表明存档仍是主矛盾。

因此，在现阶段的问题排序中，存档系统更像是已经收口的大项，而不是当前最值得优先焦虑的问题。

## 10. 当前最核心的主矛盾

当前最核心的问题不是“项目还能不能跑”，也不是“P2 有没有做完”，而是：

**项目已经越来越像一个结构完整的游戏系统，但还没有稳定地表现出一个好玩的人生模拟节奏。**

这个主矛盾可以拆成几层：

- 事件池存在，但分布不够健康
- 路线系统存在，但体感不够强
- 反馈系统存在，但重复事件会稀释反馈价值
- 验证体系存在，但体验判断能力仍偏弱

## 11. 后续新会话需要优先回答的问题

后续新会话最重要的任务，不是立刻编码，而是先回答下面这些问题：

1. 当前事件复读问题到底主要由什么造成？
2. 是单一事件冷却不足，还是同类事件分布失衡？
3. 事件池的节奏问题，是权重问题、分类问题，还是阶段分桶问题？
4. 路线系统怎样才能真正成为人生体验的主导因素，而不是旁观字段？
5. 现有模拟测试怎样才能从“能跑”升级到“能判断体验是否健康”？
6. 当前最值得先动手的问题，是事件重复、事件节奏、路线体感，还是反馈展示的进一步强化？

## 12. 使用建议

后续新会话应把本文档作为“问题定义输入”使用，而不是把它当作结论本身。

建议的新会话工作顺序应为：

1. 先读取本文档，确认当前问题边界。
2. 再结合现有模拟输出和测试报告，做只读分析。
3. 先回答“主因是什么”，再决定“怎么改”。
4. 在没有形成明确问题模型前，不要直接进入大范围实现。

## 13. 最终判断

项目当前不是“烂尾”状态，也不是“结构混乱到无法继续”的状态。

它处于一个更微妙也更常见的阶段：

**底层结构已经被整理得越来越像样，但真正决定玩家印象的那一层体验节奏，仍然没有完全站稳。**

这就是当前阶段最需要被后续会话认真思考的问题。
